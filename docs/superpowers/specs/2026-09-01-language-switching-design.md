# Language switching (EN / PT-BR) — design

## Problem

UI strings today are an inconsistent mix of English and Portuguese
hardcoded across ~107 files (`"About"` next to `"Adicionar nó"`, `"Light
Theme"` next to `"Propriedades incompletas"`). There is no i18n
infrastructure at all — no `tr()` calls, no `QTranslator`, no `.ts`/`.qm`
files. This spec adds a language switcher (English / Português (Brasil))
that the user can toggle at runtime, without restarting the app.

Scope is the application UI only — packaged docs/README are out of
scope for this change.

## Decisions

- **Languages:** English and Portuguese (Brazil), switchable at runtime
  from a menu (no restart required).
- **Mechanism:** Qt Linguist — `self.tr("...")` /
  `QCoreApplication.translate(...)` source strings, extracted with
  `pylupdate6` into `.ts` files, compiled to `.qm`, loaded via
  `QTranslator` at runtime. Chosen over a hand-rolled dict+JSON scheme
  for native PyQt6 integration and standard tooling.
- **Source language:** English. All ~107 files with Portuguese literals
  are rewritten to English source text inside `tr()`, matching the
  project's existing convention of English code/comments/commits (see
  memory `feedback_english_code_comments`). `pt_BR.ts` becomes the one
  translation file that actually needs populated `<translation>`
  entries; `en.ts` is generated but needs none (the `tr()` text itself
  is already English).
- **Default language:** detected from `QLocale.system()` on first
  launch (before any explicit user choice is persisted), falling back
  to English if the system locale isn't PT-BR.

## Architecture

### File layout

```
resources/i18n/
  circuiteditor_en.ts       (generated by pylupdate6, no translations needed)
  circuiteditor_pt_BR.ts    (generated by pylupdate6, translations filled in)
  circuiteditor_en.qm       (compiled)
  circuiteditor_pt_BR.qm    (compiled)
```

### Toolchain

`pylupdate6` is already available in the project venv
(`venv/Scripts/pylupdate6.exe`) and scans `.py` files for `tr()` calls
to produce/update the `.ts` files. `lrelease` (the `.ts` → `.qm`
compiler) is **not** bundled with the pip `PyQt6` wheel on this
machine — resolving where it comes from (a dev-only tool package, or a
small pure-Python `.qm` compiler) is the first implementation task; it
does not affect any other part of this design, since everything
downstream only depends on `.qm` files existing.

### `LanguageManager` (new module: `main_window/language.py`)

Mirrors the existing `main_window/settings.py` pattern (which already
persists font size and palette tier via `QSettings`):

- `get_language(settings=None) -> str`: reads `ui/language` from
  `QSettings("tcc-circuitos", "CircuitEditor")`; if unset, derives a
  default from `QLocale.system()` (`"pt_BR"` if the system locale is
  Portuguese-Brazil, else `"en"`) but does not yet persist it.
- `apply_language(app: QApplication, code: str, settings=None) -> None`:
  removes any previously installed `QTranslator` from `app`, loads
  `resources/i18n/circuiteditor_<code>.qm` into a new `QTranslator`,
  installs it, persists `code` to `QSettings`, and emits a
  `language_changed(code)` Qt signal from a module-level
  `LanguageManager` singleton (`QObject`).
- `app.py` calls `apply_language(app, get_language())` at startup, the
  same way it already calls
  `settings.apply_font_from_settings(app)`.

### Retranslation protocol

The app builds all widgets by hand (no Designer `.ui` forms with
auto-generated `retranslateUi()`), so switching language on a widget
that's already on screen needs explicit handling — but only for
widgets that outlive a single interaction:

- **Persistent widgets** — `MainWindow` and everything it owns
  directly (menu bar, toolbars, the actions in
  `main_window/actions/*`), the docks (`main_window/ui/docks`), the
  component palette (`main_window/ui/palette`), and any canvas item
  whose visible label is a *translated* string rather than user data
  (domain/type labels in `graphics/labels/label.py` and
  `graphics/anchors` — not node names the user typed, which are left
  untouched). Each implements a `retranslate_ui(self)` method that
  re-issues its `tr()` calls, the same content a Designer-generated
  `retranslateUi()` would contain, written by hand here. `MainWindow`
  is the single subscriber to `LanguageManager.language_changed`; it
  calls its own `retranslate_ui()` and then delegates to the
  `retranslate_ui()` of the docks/palette/toolbars it owns, rather
  than each widget subscribing to the signal independently.
- **Transient widgets** — `QMessageBox`, `QInputDialog` prompts,
  property/config dialogs, the circuit-generator dialog — need no
  hook. They're destroyed and rebuilt every time they're opened, so as
  long as every string literal is wrapped in `tr()` *inside* the
  method that builds the dialog (never hoisted to a module-level
  constant or computed once at class-definition time), they pick up
  the current language automatically on next open.

This mirrors a precedent already in the codebase: `main_window/theme.py`
had to learn the same lesson for the dark/light toggle — persistent
chrome (toolbar, menus, docks) needed explicit handling, while
per-open elements didn't.

### String migration

Sweep the ~107 files containing human-readable string literals. For
each user-facing string: rewrite to English if currently Portuguese,
wrap in `self.tr("...")` (or `QCoreApplication.translate("ClassOrModuleName",
"...")` for strings in module-level functions or `staticmethod`s with
no `self`). Out of scope: log/exception messages never shown to the
user, docstrings, comments, code identifiers.

### Switching UI

A "Language" submenu under the existing `View` menu
(`main_window/ui/menus.py`), with two checkable, mutually-exclusive
actions: "English" and "Português (Brasil)". Selecting one calls
`LanguageManager.apply_language(app, code)` immediately.

### Packaging

`CircuitEditor.spec` and `CircuitEditor-onefile.spec` (PyInstaller)
need `resources/i18n/*.qm` added as bundled data files, the same
treatment `resources/styles_*.qss` already gets — otherwise a packaged
build silently falls back to English with no error.

## Testing

- Unit: `LanguageManager` persistence and OS-locale fallback logic
  (fake `QTranslator.load`, no real `.qm` needed), following existing
  conventions in `tests/`.
- Manual/integration checklist (GUI text isn't practically
  unit-tested here): switch language with menus/toolbars/docks/palette
  visible and confirm live update with no restart; open a few
  transient dialogs in each language and confirm correct text; verify
  a packaged build locates the `.qm` files.

## Non-goals / follow-ups

- Translating `README.md` / docs — out of scope.
- 100% string coverage is not a hard gate for v1: if some corner of
  the ~107 files turns out disproportionately costly to migrate, it's
  noted as a deferred follow-up rather than blocking the feature.
